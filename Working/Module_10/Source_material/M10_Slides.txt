COMMIT MESSAGE CONVENTION


The conventions for Git commit messages play a crucial role in maintaining a clear and organized version history of a project. It's important to note that these conventions can vary significantly from one team to another, and their adoption is often influenced by the team's workflow, priorities, and preferences. In our team, we recognize the importance of a standardized commit message format for enhancing collaboration and traceability. After thoughtful consideration and collaborative discussions, our team has collectively decided to adhere to a specific convention for Git commit messages. This convention serves as a guiding framework, ensuring that commit messages are informative, concise, and consistent. By establishing and following this convention, we aim to streamline our development process, make it more transparent, and facilitate effective communication within the team.




   1. Short and Meaningful Summary:
   1. Keep the first line of the commit message concise and informative.
   2. Provide a brief summary of the changes.


   2. Use the Imperative Mood:
   1. Write commit messages in the imperative mood (e.g., "Add feature" instead of "Added feature").
   2. Maintains consistency with automated Git-generated messages.


   3. Separate Subject from Body:
   1. If needed, offer a more detailed explanation in the commit message body.
   2. Separate the subject (first line) from the body with a blank line.


   4. Limit Subject Line Length:
   1. Keep the subject line around 50 characters or less for improved readability.


   5. Reference Issues:
   1. If the commit addresses a specific issue, reference it in the commit message using keywords like "Fix," "Close," or "Resolve" followed by the issue number.


   1. Closes, Fixes, Resolves:
   1. These keywords automatically close an issue when the commit is merged.
   2. Example: Closes #123, Fixes #456, Resolves #789.


   2. References, Refs, Addresses:
   1. These keywords reference an issue or pull request without automatically closing it.
   2. Example: References #123, Refs #456, Addresses #789.


   3. Related:
   1. Indicates that the commit is related to an issue or pull request.
   2. Example: Related to #123.


   4. See Also:
   1. Used to provide additional references.
   2. Example: See Also #123.


   5. Implements:
   1. Indicates that a commit implements a certain feature.
   2. Example: Implements #123, Implements feature/xyz.


   6. 6. Commit Message Keywords:
   1. Feat:
   1. Short for "feature," indicates the introduction of a new feature.
   2. Example: feat: add user authentication.


   2. Fix:
   1. Indicates a bug fix.
   2. Example: fix: resolve issue with user login.


   3. Chore:
   1. Used for tasks or changes that are not user-facing or are maintenance-related.
   2. Example: chore: update dependencies.


   4. Docs:
   1. Used when updating documentation.
   2. Example: docs: update README with new instructions.


   5. Style:
   1. Indicates changes that do not affect the meaning of the code (e.g., formatting).
   2. Example: style: format code according to style guide.


   6. Test:
   1. Used for adding or modifying tests.
   2. Example: test: add unit tests for user authentication.

Admin Section
________________


 
 
Now that we have a working website with some basic features, we're going to need an Admin section for our client.  In this Admin section, they're going to need the power to control the content that users make (since we don't want things like bullying or harassment to take place on our platform), and the power to edit the CodeBloggs User base.
  
 
User Manager
  

 
The User Manager will list out all the current users, but with CRUD functionality. The authorized Admin should be able to Edit and/or Delete a User.  When clicking on a User, this should take you to a details page (or open a modal) where the admin will have access to edit the info of the User. 
By default, all users should be displayed using a pagination system that shows 10 users per page, along with a dropdown allowing the user to adjust how many users are displayed per page (e.g., 10, 15, 20, etc.).
 
The fields we could use for this include first_name and last_name.  The other columns will be Edit and Delete.  You're free to style these up in any way you see fit.  Much like the Agents table in previous weeks, you should be able to sort the list of Users alphabetically by first name, or last name.
 
Somewhere at the top, we'd also like to have a search button that will filter out Users by first name or last name.
 
 
Content Manager
  

 
The content manager should really only manage one thing about our content, which is the blogg post.  And we should really be able to edit anything here, so the only CRUD feature we need for this is Delete.  By default, all posts will be shown when the user first loads up the screen.
 
Like the User Manager section, we want to implement a search functionality that should search by a range of dates.
 
Pagination system that shows 10 posts per page should be implemented as well, along with a dropdown allowing the user to adjust how many posts are displayed per page (e.g., 10, 15, 20, etc.).
 
 
Modal
A few weeks back we added popup modals that would give a user a confirmation making sure that we wanted to delete the agent.  We're going to implement that again, but this time for Posts and Users.
 
 
Skeleton Loader
Once you're complete with the implementation of the User and Content Manager sections, you can then add the feature of a Skeleton Loader.
 
You've probably seen this feature in other sites like YouTube or other big applications that require a lot of data processing.  Essentially, skeleton loading is something you'd see as a placeholder to where data is going to go after it's loaded. Reactive and Responsive Design
________________


 
 
In this section, we want you to think about how the website not only looks and feels on a desktop, but on a mobile device or tablet.  With the research that we did earlier, we should be able to tackle our Reactive and Responsive design.
 
 
Reactive Design
There's a lot you could get into with Reactive design, but what this essentially means is things will be happening on the website while our data is loading in the background from our database.  For the time being, the only type of Reactive design we would like you to focus on would be the Skeleton Loaders in the Admin section, and if you finish the project early, you can dive deeper into Reactive design with the bonus material.
 
 
Responsive Design
At the moment, our website looks great!  But...have you tried squeezing the sides for a smaller view port?  Or even looking at it through a mobile device with your DevTools?  Chances are, unless you already had this in mind, that something is broken, or looks off, or doesn't fit with the look you're trying to go for.
 
This is where Responsive Design comes in.  Once our screen starts to move elements in ways that weren't designed originally, we're going to need to add to our CSS in order to correct this behavior.  Media Queries in CSS is a great place to start
 
We should have a view as a full page, a tablet view, and a mobile view.  It'll be up to you to figure out the sizes that these should be!
